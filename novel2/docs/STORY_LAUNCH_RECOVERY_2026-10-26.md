# Interactive Novel 2.0 — восстановление запуска

Дата: 26.10.2026. Цель: убрать зависимость создания первой главы от одного открытого HTTP-соединения и исключить автоматический повтор платной генерации.

## Основание

Пользовательский сбой: «История оживает…» → `Load failed`. Проверка кода выявила последовательное создание ролей, изображений и первой главы внутри одного запроса; шлюз мог повторить этот POST при транспортной ошибке. Это подтверждённые дефекты устойчивости; точную причину конкретного сетевого обрыва без серверного журнала установить нельзя.

## Изменение

- Старт быстро возвращает сохранённую задачу; отдельный запрос читает её состояние.
- PostgreSQL хранит этапы, завершённые результаты и ID готового романа. Эти приватные промежуточные данные не возвращаются клиенту и очищаются после успешного завершения.
- Блокировка на отдельном соединении с БД исключает параллельную генерацию для одной пары, в том числе из другого процесса. Повторный запрос с тем же черновиком возвращает существующую задачу.
- Создание романа, первой сцены, состава персонажей, перевод черновика в использованные и готовность задачи выполняются одной транзакцией. Ошибка сохраняет прежний роман.
- При закрытии окна сервер продолжает работу. После открытия приложение проверяет сохранённую задачу; при потере связи предлагает проверку статуса вместо повторной генерации.
- После ошибки или остановки процесса нет автоматического повтора AI-вызова. Пользователь может явно продолжить с сохранённого этапа; предупреждение сообщает, что последний незавершённый запрос может повториться. Это не обещание однократной оплаты на стороне внешнего провайдера.
- Шлюз повторяет только разрешённые операции чтения. POST запуска, ответа и создания истории не переотправляются автоматически.
- Проверка наличия нового status API защищает от вызова старого синхронного обработчика во время поэтапного обновления интерфейса и сервера.

## Проверки

Модульные: потерянный ответ запуска, повторное открытие, недоступный старый сервер, явное продолжение, конкурирующие окна/процессы, приватность статуса.

Изолированный PostgreSQL в CI: реальная advisory-блокировка, повтор завершённой публикации, атомарная запись первой главы и состава, откат ошибки, сохранность активного романа и черновика, продолжение после остановки процесса.

Шлюз: один запрос для изменяющих операций, повтор чтения статуса, буферизация коротких ответов, доставка нового клиентского скрипта. Платные AI-запросы не входят в эти проверки.

## Внедрение и пределы

Данные остаются в существующей базе Novel 2; добавляется таблица задач без удаления прежних записей. Это исправление текущего runtime, а не завершение переноса всего романа в Cloudflare. В текущей реализации AI-исполнитель всё ещё зависит от работающего origin-сервиса. При падении процесса этапы сохраняются, но продолжение требует явного действия пользователя.

Worker и интерфейс публикуются штатным workflow. Origin обновляется отдельным штатным deployment bridge. До проверки обоих компонентов и входа с телефона исправление нельзя считать полностью внедрённым. Не запускать новую платную генерацию ради диагностики; сначала проверить сохранённую библиотеку и состояние задачи.

Откат: вернуть предыдущую версию приложения и Worker; новую таблицу не удалять. Откат во время активной генерации выполнять только после её окончания, иначе задача останется для явного продолжения.

## Изоляция от автообновления бота

API романа проверяет Telegram-подпись, но не получает обновления Telegram. В контейнере проверочный ключ передаётся как `NOVEL2_TELEGRAM_AUTH_TOKEN`; общие переменные `TELEGRAM_BOT_TOKEN` и `BOT_TOKEN` явно очищены, включая значения из env_file. Это не позволяет автообновлению бота ошибочно остановить роман как конкурирующий polling-процесс. Формат входного .env остаётся прежним; standalone-конфигурация со старым именем поддерживается. Тест подписанного входа проверяет обоих игроков, отказ постороннему и совместимость старой настройки.
